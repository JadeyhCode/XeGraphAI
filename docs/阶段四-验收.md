## 六、已知边界（照实说，别再重复问）

1. **能力 = 知识**：图里没有的任务/片段/模板，一条也写不出来（C1 就是这条的证据）。
2. **检索是子串匹配**：关键词没有词边界、没有否定处理 ——「不要写素数」也会命中素数。
3. **组合是线性拼接**：片段顺序靠"依赖排序"（§6.708：子串判据 + 冒泡松弛），
   模板永远第一、主体永远最后；片段 >16 个会**静默丢**多余的（没报错）。
   依赖判据只认"代码里出现另一个片段的名字"：注释/字符串会误判成依赖，
   改名调用/函数指针会漏判；成环时放弃排序。
4. **单文件、只有 C11**：多文件工程、别的语言都不在范围内（`::code build` 能编多文件，但合成只到单文件）。
5. **消融只做了"删代码边"**：全删（C1）与只删片段（C2）；"删关键词边""换错骨架""删模板"没做。
6. **真知识 10⁶ 边已经能到（§6.709：1 261 334 边），但性能不达标**：载入 3.08 s / RSS 1.40 GB /
   存盘 4.35 s，三条都超 M3 目标 ⇒ 默认仍是 406 125 边的公共 API 版。要拿它当默认，
   先做阶段三 M2-3「边打包 + 字符串池」。**§6.702 那句"真知识上不了 10⁶ 边"是错的**
   （真原因：`INC` 只扫了 `/usr/include`，全机有 59 527 个 `.h`）。
7. **`.c` 片段知识已进图（§6.710），但合成器还不会自动用**：图里从 3 个手写片段涨到 **1 124 个**
   真实函数体（298 个"独立"），但 `::code synth` 的组合仍靠 `任务 --用--> 片段` 的**手写边**
   ⇒ B 段一条都没变（15/15 是"没被弄坏"，不是"变好"）。自动检索片段是下一步。
8. **两侧单条查询延迟没在 10⁶ 边上量**（只量了载入/存盘/RSS 和 B 段通过率）。

## 七、0.5B 边（5×10⁸）：分片语料 + 局部加载（§6.706）

### 结论先说

**0.5B 不是"一张图全装进内存"，而是 25 个 2000 万边的分片落盘（28 GB），每次只激活一片。**
依据：全装需 ≈91 GB（182 B/边实测），本机 15 GB —— 差 8 倍，单文件全装在本机不可能。

### 实测数字（全部可复现）

| 项 | 数值 | 怎么量的 |
|---|---|---|
| 分片总量 | **25 片 × 20 000 205 边 ≈ 5.0×10⁸ 边** | `::stats` 数了 shard_01 与 shard_25 |
| 总落盘 | **28 GB** | `du -sh /mnt/models/aip-corpus-0.5B/big` |
| 单片 | 400 449 词 / 20M 边 / 模型 1.10 GB | `ls -l` + `::stats` |
| parts 打包 | **每片 1 个文件**（1.2 GB，400 079 段） | `::parts save` + `find \| wc -l` |
| parts save | 2M 边 7.3 s（20M 边约 90 s 量级） | `/usr/bin/time` |
| **attach（只挂索引）** | **0.10 s / RSS 15 MB** | `/usr/bin/time` |
| detach | 65 510 个词的边离开内存，查询时按需读回 | `::parts detach` + `::rel` 能答出 |
| 跨片正确性 | 同词 `w000001`：A 片给出 w020170/w020171，B 片给出 w063709/w063710 | 两片分别 attach 后 `::rel` |

### 负结果（必须照实写）

- **`detach` 不降低"峰值 RSS"**：仅加载 3 632 160 KB，attach+detach+查询 3 632 324 KB —— 峰值出现在加载阶段（建 20M 条边），detach 发生在之后。所以"内存降 90%"这种说法是**错的**；能说的是"边可以换到磁盘、按需读回"。
- **`attach` 只挂索引，不合并语料**：在只有 1271 词的 `model.bin` 里 attach 一个 40 万词的分片，查 `w000001` 会答"不在图里"、`::parts stats` 显示"读回 0 段"——因为那个模型里没有这个 token，也就没有可解析的哨兵。`::parts` 的语义是"**同一张图的边外置**"，不是"跨语料合并"。
- **跨片 = 换片**：要做"一张 0.5B 的单图"必须新做分片命名空间 + 索引合并（路线 B），本轮没做。

### 一句话

**分片路线（路线 A）已经打通并验证**：单片 3.63 GB 峰值、索引 attach 0.1 s/15 MB、边按需读回、跨片答案随激活片变化。**路线 B（跨片单图）未做**，需要新功能。

## 九、7B 边分片语料（§6.711；用户 2026-11-03 追加目标）

**是什么**：7 000 000 000 条边、**350 片 × 2000 万边**、每片一个 `.c7b` 文件（**8 B/边**），
合计 **58.2 GB**；挂上一片只读 48 字节头，查一个词按需读那一段（实测 512 字节）。

**为什么换格式**：0.5B 那批每片是完整模型（**59.2 B/边**）、`::parts` 是 **64.4 B/边**
⇒ 7B 要 414 / 451 GB，而 `/mnt/models` 只剩 327 GB。`.c7b` 只存边（邻居 + 关系）⇒ 58 GB。

**怎么用**：`::parts corpus <片.c7b>` / `::parts corpus rel w000042` / `::parts corpus stats`。

**证据**：`tests/corpus7b.sh`（9 项：确定性、每片自洽、段内无重复、断点续跑、引擎可挂可查、
坏文件拒）；`tools/gen_corpus7b.sh --verify-only` 重算总边数；清单 `manifest.txt` 记每片边数/字节。
**边界**：不是一张单图（350 次独立抽样、无跨片边）；引擎只接了 `::parts corpus` 这一条读法
（`::rel`/求解器还没接）；7B 全是**合成边**，不是知识。详见 `docs/7B-边语料.md`。

### 9.7 内存构成实测（为什么 RSS 还差 180 MB）

用 `mallinfo2` + 逐项统计（`AIP_LOADDBG`，测量代码已撤，不留调试侵入）：

| 项 | 大小 |
|---|---|
| Token 结构 | 658 893 × 320 B ≈ **201 MB** |
| AssocEntry（sumcap 2 197 544 × 72 B） | ≈ **150 MB** |
| 名字 | ≈ **18 MB** |
| 反查表 rev（1 077 067 × 12 B） | ≈ **12 MB** |
| NameEntry + 桶 | ≈ **34 MB** |
| **每词一份 emb（658 893 × 1 024 B）** | **≈ 674 MB** ← 主因 |
| 其它（AI 层、关系表、槽类、idf…） | 余下 |

结论：**RSS 的 60% 是每词一份的 1 KB emb**，它在 `pool_token` 里 `calloc(EMB_DIM)` 就分配了，
即使 `emb_deferred` 把**计算**推迟了，**内存**也没省。

要把 RSS 压到 ≤1 GB，下一步是**emb 惰性分配**：创建词时不分配，`ai_embed_build` 时统一建；
风险点是 42 处 `->emb` 读取里少数没有判空（`ai.h:3244/3335` 是构建路径，`5127/5141/5143`
是相似度路径），要先逐处加空判据或共享零向量，再跑整包 + `conc_tsan`。

存盘/载入时间侧的下一步仍是：边先编码进栈缓冲一次性写入（减少每字段函数调用）、
以及 `cap` 精确分配（当前 1 条边的词也占 4 条边的内存，约 100 MB）。

### 9.6 空符号改为**匿名**（按用户 2026-11-13 澄清）

- `xe.h` 的 `xe_hole` 不再生成 `空:词:义` 这种带语义的名字，改为 `空#n`；

- 取第 n 个空改为**建边顺序**（匿名名字不能拿来排序）；
- 学习写补丁时记录空符号**真实的名字**（`空#n`），重放才接得上。
