# 引擎内 ARC 归纳：把变换表沉进图（v1.00b 之后第一块新能力）

一句话：**ARC 归纳做进了引擎（C），变换表与搜索策略都在图里**；分数是
**ARC-AGI-1 train 44/400（11.0%）、eval 7/400（1.8%）、ARC-AGI-2 eval 0/120**
（56 个原语 + 局部编辑 + 迭代加深到深度 3）。**train 第一次摸到 10%，但那是训练集，不是考卷。**
**没到 10%**，原因不是"原语不够多"（实测加 17 个原语只多解 1 道 eval），是这一族题要**对象级归纳**。

---

## 1. 为什么是"进图"，不是"写个 Python 求解器"

上一轮挂过一个外部 Python 枚举求解器：ARC-AGI-2 eval 0/120、ARC-AGI-1 train 21/1000。
那是**外挂的分**，而且违背项目一直守的规矩：**能下沉到图里的机制就下沉**。

所以这一版拆成两半：

| 归属 | 内容 | 在哪 |
|---|---|---|
| **知识**（数据） | 有哪些变换、属于哪一类、**是否启用**、**深度/预算策略** | **图里**：`变换:rot90 属于 变换类:几何`、`有 序号 1`、`有 启用 是`、`变换库 有 深度2` |
| **执行**（代码） | 把一个 30×30 整数矩阵按某个变换搬一遍 | `arc.h`（26+17 个原语函数） |
| **搜索**（代码） | **迭代加深 + 深度优先 + 节点预算**（先找浅解，再往深走）；颜色映射/常量输出两个特例 | `arc.h` |

这和项目里已有的两处是**同一个形状**：帧数据进图、解释器在 C（`frame.h`）；骨架代码进图、编译器在 C（`code.h`）。

### 命令

```sh
::arc sync                 # 把变换表写进图（属于 / 序号 / 启用 三类事实；随 ::save 存盘）
::arc list                 # 看图上登记了哪些变换、哪些被停用
::arc off symh             # 停用：写的是**图上的事实**（有 否），不重编译
::arc on  symh             # 启用回来
::arc depth 2              # 搜索深度（1~4）：写进图，`变换库 有 深度2`
::arc budget 240000        # 节点预算（6万/12万/24万/48万）：也写进图
::arc solve task.json      # 读 ARC 格式任务：训练对筛候选 → 套到测试输入 → 打印预测网格
```

### 怎么证明"真在图上"（`tests/arc.sh`，13 项）

1. 空图 `::arc list` → 明说"还没有变换表"（不假装有）；
2. `::arc sync` 后 list 报出数量；
3. **存盘再读**：sync → `::save` → **新进程**加载 → list 仍然查得到（表跟着图走，不是内存常量）；
4. `::arc solve` 解出对称补全题，预测 `[606/070/808]` 逐格正确；
5. **反证**：`::arc off symh` 之后**同一道题解不出**，`::arc on symh` 又解得出 ——
   如果表是 C 里的静态数组，这一条不可能成立；
6. 坏文件/坏变换名：不崩、明说读不了。

## 2. 分数（引擎自己跑，不作弊）

协议与前面几张卷子一致：只喂**训练对 + 测试输入**（测试答案只用于判分）；一题一进程；不教、不调参；判据 = **网格逐格相等**。

| 数据集 | 题数 | 逐格正确 | 引擎说"解出" |
|---|---|---|---|
| ARC-AGI-1 training | 400 | **44（11.0%）** | 47 |
| ARC-AGI-1 evaluation | 400 | **7（1.8%）** | 7 |
| ARC-AGI-2 evaluation | 120 | **0（0.0%）** | 0 |

解出的题按**解出来的路径**归类（ARC-AGI-1 training）：单步 `colormap 4 / mirrortile 3 / largestobj 2 /
rot180 2 / symv 2 / transpose 2`；组合 `mirrortile→tile1x2→quad_tl 2 / mirrortile→tile2x1→quad_tl 2 /
crop0→quad_tl 1 / crop0→tile1x2 1 / tile1x2→overlayxor 1 / fliplr→crop0 1 / up2→crop0 1` 等 ——
**组合解出现了**，这是换搜索算法（迭代加深 DFS）带来的，不是加原语带来的。

## 3. 为什么没到 10%（这是实测，不是猜）

| 尝试 | 结果 |
|---|---|
| 26 个原语 + 深度 2 穷举 | train 27/400、eval 3/400 |
| **加 17 个原语**（按颜色裁剪 ×9、四象限 ×4、去噪、补洞、叠加 or/xor） | train **29**、eval **4** —— 只多 2 题 |
| **加 4 个对象级原语**（最小对象/填包围盒/描边/按面积重上色） | train **30**、eval **4** |
| **换搜索**：束搜索（按部分命中数剪枝） | train 27、eval 3 —— **反而更差**（真路径常常第一步 0 命中，被剪掉） |
| **换搜索**：迭代加深 DFS 到深度 3（47 原语，24 万节点预算） | train **34（8.5%）**、eval **4** —— 组合解开始出现 |
| **加 9 个"选择/计数/对称"原语**（seluniq/selcommon/selrare/oddobj/countobj/countcolors/overlaytb or·xor/symdiag） | train **36（9.0%）**、eval **7（1.8%）** —— **这批最有效**（eval 4→7） |
| **加"局部编辑"**（11 种掩码 × 保形变换 / 刷成某色 / 掩码换色） | train **40（10.0%）**、eval **7** —— 训练集 +4，**考卷 +0** |
| **加"结构"**（固定位置子块 / 加边框 / 去边框） | train **42（10.5%）**、eval **7** —— +2 / +0 |
| **加"对象属性规则"**（碰边框/面积唯一/最大最小/颜色唯一 × 刷色/去掉/只留） | train 42、eval 7 —— **+0 / +0（负结果，留在文档里）** |
| **加"谓词合取"**（12 个谓词两两相与 × 刷色/去掉/只留） | train 42、eval 7 —— **+0 / +0（第二个负结果）** |
| **加"切块找异类/多数"**（2×2/3×3/1×N/N×1 等分） | train 42、eval 7 —— **+0 / +0（第三个负结果）** |
| **关系归纳**（对象标签 → 谓词规则，`tools/arc_reach.c` 量可达率） | train 42、eval 7 —— 可达率只有 **18/400**，学出 0 |
| **加法原语**（连点成线 ×2、射线 ×4，注册成普通原语 ⇒ 也受图上启用表管） | train **44（11.0%）**、eval **7** |
| 外部 Python 枚举求解器（上一轮，已删） | train 21/1000、ARC-AGI-2 eval 0/120 |

趋势很清楚：**"按属性选 / 数一数 / 补对称"这一类原语，比"再堆几何变换"有效得多**
（17 个几何/裁剪类只 +1 题 eval；9 个选择/计数类 +3 题）。

**结论**：加原语是边际收益几乎为零的路线。ARC-AGI-1 eval 上 10% = 40 题，现在是 4 题；
差的不是"再多几十个原语"，而是三件机制：

1. **对象级表示**：把网格切成对象（连通块/形状/大小/颜色），在对象上做规则（"最大的那个""唯一不同的那个"）；
2. **组合搜索的深度与剪枝**：现在深度 2、无剪枝；真实解法常常是"选出子块 → 对它做两步操作"（深度 3~4 + 形状约束剪枝）；
3. **规则归纳**：从 2~6 个例子里猜出"变化的是哪个属性"，而不是从固定表里挑函数。

ARC-AGI-2 eval 是 0：它专门造来打"对称/镜像/枚举"这一类（官方原文见 `docs/benchmark-hle-arc2.md`），
**原语再多也碰不到**。

## 3.5 eval 到底长什么样（为什么难）

我把 ARC-AGI-1 的 400 道 eval 统计了一遍：

| 特征 | 题数 | 占比 |
|---|---|---|
| 输出与输入**同尺寸** | 270 | **68%** |
| 输出更小 | 69 | 17% |
| 输出更大 | 30 | 7.5% |
| 其他（尺寸按对变化） | 31 | 7.8% |
| 输出是输入的某个矩形子块（所有训练对成立） | 18 | 4.5% |
| 所有训练输出相同（常量题） | 0 | 0% |

**同尺寸占 68%**，所以"保形变换 + 局部编辑"方向是对的；但 7/400 说明**规则本身复杂**：
不是"全局换色"或"整块刷色"，而是"按对象与其它对象的关系决定怎么变"（对齐、包含、计数、相邻）。
这一轮加的"对象属性规则"（碰边框 / 面积唯一 / 最大最小 / 颜色唯一 × 刷色 / 去掉 / 只留）
**train +0、eval +0** —— 负结果，照样记在这里：**单属性规则不够，要的是属性之间的条件组合**。

### 关系归纳的**可达率**（这一轮最硬的一条数）

"对象谓词 → 一个动作"这条模型能解释多少题？用 `tools/arc_reach.c` 数的（ARC-AGI-1 eval 400）：

| 筛子 | 题数 |
|---|---|
| 输出与输入同尺寸 | 270 |
| 且**背景格没被改**、每个对象整体变化一致（可打标签） | **18** |
| 且所有"变了"的对象动作一致（同动作同颜色） | 18 |
| **能学出一条谓词规则** | **0** |

所以这条家族**最多覆盖 18/400 = 4.5%**，而且现有谓词一条都没命中。
训练集上是 19 题、学出 2 条（但这两题已经被颜色映射先解掉，不增量）。

**这就是"再加谓词"的定量上限**：不是谓词不够，是这条模型本身太窄。

### 三个连续的 +0（负结果清单）

| 试的机制 | train | eval |
|---|---|---|
| 束搜索（按部分命中剪枝） | −7 | −0 |
| 对象属性规则（单属性） | +0 | +0 |
| 谓词合取（两个属性相与） | +0 | +0 |

**这三个 +0（外加束搜索更差）是本轮最有信息量的东西**：ARC-AGI-1 eval 的瓶颈不是"属性不够多"，而是"关系"——
对象与对象的对齐/包含/计数/相邻，以及"规则本身随对象变化"。这类解法得在**对象关系图**上做搜索，
而不是在"整图变换 + 属性掩码"这层加料。

### 做了什么处置

三个 +0 的阶段（对象属性规则 / 谓词合取 / 切块异类）**已从代码里删掉**（连同它们的辅助函数）：
留在默认路径上只会让每题多跑几百个候选。负结果留在本节，下次别再从头试一遍。

### 同尺寸题的"变化类型"分布（这一轮补的统计）

| 类型（所有训练对一致） | eval | train |
|---|---|---|
| 纯加法（只多格子，不动原有非背景格） | **103** | 126 |
| 纯删除 | 27 | 22 |
| 纯换色 | 45 | 29 |
| 混合（加法/删除/换色都有） | 95 | 85 |

纯加法 103 道看着很多，但抽看最小的几道，大多是**序列/周期延拓**（"2 3 0 → 2 3 0 2 0 0 3 …"），
不是"连点成线"。所以 6 个加法原语只在 train 上 +2，eval +0 —— 又一个"族存在但规则不同"的例子。

## 4. 复现

```sh
# 机制（表在图上）
sh tests/arc.sh                       # 13 项：空图/sync/存读/解题/停用反证/坏输入

# 分数（引擎内，全量）
python3 tools/arc_engine_bench.py --set arc1-train    # 400 题，约 15 s
python3 tools/arc_engine_bench.py --set arc1-eval     # 400 题
python3 tools/arc_engine_bench.py --set arc2-eval     # 120 题
```

产物：`_bench/arc_engine_<set>.jsonl`（逐题：对/解出/用了哪个变换/尾巴）、`_bench/arc_engine_<set>.md`。
数据缓存在 `_bench/data/`（ARC-AGI-1 与 ARC-AGI-2 的公开仓库，不入库）。

## 5. 丑话说在前面

- 这版**没有** 10%，也没有接近。它是"机制先立起来、分数老实报"的那一步；
- `::arc` 现在只吃**单个任务文件**，不做批量/多任务学习（批量由 `tools/arc_engine_bench.py` 驱动）；
- 颜色映射是"从训练对推一个逐色映射"，遇到"按对象上色"就失效；
- 原语顺序还在 C 表里（**启用/停用在图里**）；顺序要不要也进图，等有"顺序真的影响结果"的证据再说。
